# AI辅助开发：流程、规范与方法

适用于个人与小团队 · v1.0

## 1. 目的与核心原则

本文档规定如何用AI写代码，同时保证代码质量可控、审核成本可控、设计意图不丢失。

**核心原则**

1. **人负责判断，AI负责执行。** 需求、边界、责任范围、状态机由人最终拍板；AI不得替人做这些决定。
2. **文档是唯一事实来源。** 需求与设计写进仓库，代码与文档冲突时先改文档再改代码。
3. **前置门禁。** 上一阶段未确认通过，不进入下一阶段，尤其是需求阶段。
4. **AI不得静默填补空白。** 遇到歧义必须提问或明确列为“假设”，不允许悄悄猜。
5. **小步提交。** 每次改动小到人能真正审完。
6. **测试独立于实现。** 测试依据需求生成，而不是依据代码生成。
7. **审核精力按风险分配。** 需求 > 业务流程/状态机 > 表结构/核心后端逻辑 > 样板代码。
8. **不理解的代码不合并。**

## 2. 角色与分工

| 事项 | 人 | AI |
| --- | --- | --- |
| 需求范围、边界、责任归属 | 决策、确认 | 提问、整理、列假设与未决问题 |
| 业务流程、状态机 | 决策、审核 | 起草、枚举状态与转换、找漏洞 |
| 方案设计 | 选型决策 | 给出备选方案与取舍 |
| 表结构、核心逻辑 | 重点审核 | 起草、自查 |
| 样板代码、CRUD、工具函数 | 抽查 | 生成 |
| 测试场景 | 审核场景是否覆盖需求 | 生成用例 |
| 代码审查 | 看高风险点与偏离点 | 独立会话做首轮审查 |
| 合并决定 | **最终决定** | 不得自行合并 |

## 3. 总体流程

```
阶段0 准备 → 阶段1 需求 → 阶段2 方案设计 → 阶段3 影响分析
→ 阶段4 测试用例 → 阶段5 分步实现 → 阶段6 审查 → 阶段7 合并与复盘
```

每个阶段都有**产出物**和**准出标准**。准出由人确认，确认前不进入下一阶段。

**允许回退：** 任何阶段发现上游问题，退回修改上游文档，再重新走后续阶段，不在代码里打补丁绕过。

## 4. 各阶段规范

### 阶段0：准备（一次性 + 随项目维护）

- 建立项目规则文件（见第8节），写明技术栈、目录结构、风格约定、禁止事项、工作流约定。
- 建立文档目录，例如：

```
docs/
  requirements/   需求文档
  design/         方案设计
  impact/         影响分析
  decisions/      关键决策记录（ADR）
```

- 配置自动化兜底：lint、格式化、类型检查、单元测试、CI。

### 阶段1：需求（最重要，门禁最严）

**做法：** 你先口述想法与背景，让AI先**提问**，再整理成文档。多轮迭代，直到你认为无歧义。

**产出：** `docs/requirements/<名称>.md`，必须包含：

- 背景与现状、存在的问题
- 目标（要达成什么，尽量可验证）
- **非目标**（这次明确不做什么）
- 范围与边界（涉及哪些模块、数据、用户角色）
- **责任范围**（哪些由本系统负责，哪些由外部系统或人负责）
- 核心业务流程
- 异常与边界场景（空值、重复、并发、超时、部分失败、权限）
- **AI的假设清单**（逐条标注：已确认 / 待确认）
- **未决问题清单**
- 验收标准

**准出标准：**

- 假设清单全部由人确认，未决问题清零或明确推迟并记录原因
- 非目标和责任范围已写明
- 人能用自己的话复述这个需求的边界

### 阶段2：方案设计

**产出：** `docs/design/<名称>.md`，必须包含：

- 总体方案，**至少两个备选方案**及取舍理由，最终选择与原因
- 业务流程图或时序
- **状态机**：状态列表、转换表（当前状态、事件、条件、目标状态、副作用）、非法转换如何处理
- 数据库表结构：字段、类型、约束、索引、迁移与回滚方式
- 接口设计：入参、出参、错误码、幂等性
- 事务边界与并发控制
- 关键异常处理策略

**准出标准：**

- 设计逐条对应需求，没有“需求里没有、设计里多出来”的内容（有则说明理由）
- 状态机的每个转换都能追溯到需求
- 人理解并认可选型理由

### 阶段3：影响分析

**产出：** `docs/impact/<名称>.md`，包含：

- 受影响的模块、接口、数据、定时任务、下游系统
- 历史数据兼容与迁移方案
- 性能与容量影响
- 安全与权限影响
- 上线步骤、灰度方案、**回滚方案**
- 风险清单与应对

**准出标准：** 回滚方案可执行，兼容性问题有结论。

### 阶段4：测试用例（先于实现）

**依据需求和设计生成，不依据代码。**

- 用例分为：验收用例（来自需求）、状态机用例（每个合法转换与每个非法转换）、边界与异常用例、并发与幂等用例、回归用例。
- AI须标注每个用例对应的需求条目；**自行补充的用例单独标记**。
- 人审核的是“场景是否覆盖了需求和边界”，这一步本质上是第二次审需求，常能发现新问题。

**准出标准：** 需求的每一条验收标准至少有一个用例；状态机转换表覆盖率为100%。

### 阶段5：分步实现

- 把设计拆成**可独立验证的小任务**，每个任务一次小提交，每次提交的diff以人能审完为准。
- 每个任务的指令必须包含：任务目标、相关文档路径、允许修改的文件范围、验收方式。
- 实现过程中必须遵守：
  - 不修改范围外的文件
  - 不引入未经批准的依赖
  - 不吞异常，不用默认值掩盖错误
  - 遇到歧义先提问
  - 不为了通过测试而修改测试或写死结果；如认为测试有误，必须说明并由人决定
  - 发现需求或设计有问题，停下来报告，不自行绕过
- 每个任务完成后必须本地跑通：lint、类型检查、相关测试。

### 阶段6：审查

分三层：

1. **机器审查**：lint、类型检查、测试、依赖与安全扫描。能自动检查的不消耗人的注意力。
2. **AI独立审查**：开**全新会话**（不带实现过程的上下文），只提供需求、设计、diff，要求输出：
   - 代码与设计的偏离点及原因
   - 范围外的改动
   - 风险最高、最需要人工确认的5个点
   - 边界与并发问题
3. **人工审查**：按第5节的分级策略，重点看AI给出的高风险点与偏离点。

**准出标准：** 偏离点要么修正代码，要么回退修改设计文档，不允许“代码与文档不一致”的状态合并。

### 阶段7：合并与复盘

- 合并前检查清单（见第9节）全部通过。
- 更新文档，使其与最终实现一致。
- 简短复盘：AI哪里出错了？哪类问题漏过了审查？把教训写进规则文件或提示词模板。

## 5. 审核策略：按风险分级

| 级别 | 内容 | 审核方式 |
| --- | --- | --- |
| S级 | 需求、边界、责任范围 | 人逐条确认，不外包给AI |
| A级 | 业务流程、状态机、并发、幂等、权限 | 人逐条审，对照转换表 |
| B级 | 表结构、迁移、事务边界、核心后端逻辑 | 人重点看约束、索引、事务、可回滚性，AI辅助 |
| C级 | 样板代码、CRUD、工具函数、简单前端 | AI审查 + 测试兜底，人抽查 |

**人工审代码的清单：**

- diff范围是否超出任务范围
- 是否有未要求的功能、抽象或依赖
- 异常是否被吞掉，错误是否被默认值掩盖
- 空值、重复、并发、超时、部分失败是否处理
- 是否调用了不存在的API或库函数
- 测试是否被改动或写死
- 日志、敏感信息、权限校验
- 自己能否解释清楚这段代码为什么这么写

## 6. 测试规范

1. 测试来源于需求与设计，先于实现生成并经人审核。
2. 状态机：每个合法转换、每个非法转换都有用例。
3. 必须覆盖：边界值、异常路径、重复提交、并发、幂等。
4. 关键逻辑可做**变异检验**：让AI故意改坏代码，确认测试能失败。
5. 禁止为通过测试而修改测试预期；确需修改测试，必须说明理由并经人确认。
6. 缺陷修复遵循：先写能复现缺陷的失败用例，再修复。

## 7. 提示词模板

### 7.1 需求阶段

```
你是资深需求分析师。我会描述一个需求，请先不要写文档。
第一步：向我提问，找出范围、边界、责任归属、异常场景上的所有不确定之处，每轮最多10个问题。
第二步：等我回答并确认后，再按以下结构输出需求文档：
背景与现状、问题、目标、非目标、范围与边界、责任范围、业务流程、异常与边界场景、验收标准。
要求：
- 凡是我没有明确说过、由你推断的内容，一律列入“假设清单”，不得写成既定事实。
- 无法确定的列入“未决问题”。
- 不要擅自扩展需求，不要加入我没提到的功能。
```

### 7.2 方案设计阶段

```
基于 docs/requirements/xxx.md 输出方案设计。
要求：
- 给出至少两个备选方案，对比复杂度、风险、可维护性、对现有系统的影响，并说明推荐理由。
- 设计状态机：状态列表、转换表、非法转换处理。
- 设计表结构：字段、约束、索引、迁移与回滚。
- 标明设计中每一项对应需求的哪一条；需求里没有的内容请单独列出并说明为什么需要。
- 列出你的假设与不确定点。
```

### 7.3 测试用例阶段

```
基于需求文档和设计文档生成测试用例，不要参考任何现有实现代码。
要求：
- 每个用例标注对应的需求条目。
- 状态机的每个合法转换和非法转换都要覆盖。
- 覆盖边界值、异常、重复提交、并发、幂等。
- 你自行补充（需求中没有明确要求）的用例，单独分组标记。
```

### 7.4 实现阶段

```
任务：实现 <任务描述>。
参考文档：<文档路径>。
允许修改的文件：<范围>，其他文件不要改。
要求：
- 严格按设计文档实现；发现设计有问题请停下来告诉我，不要自行变通。
- 不引入新依赖，不吞异常，不为通过测试而修改测试。
- 有歧义先问我。
- 完成后运行 lint、类型检查和相关测试并报告结果。
- 最后列出：本次改动的文件、与设计的任何偏离、你不确定的地方。
```

### 7.5 独立审查（新会话）

```
你是严格的代码审查员。以下是需求文档、设计文档和本次diff。
请输出：
1. 代码与设计的偏离点（逐条，含原因判断）。
2. 范围外的改动。
3. 边界、并发、幂等、事务、权限方面的问题。
4. 风险最高、最需要人工确认的5个点。
5. 可疑的“为了让测试通过”的改动。
只指出问题和依据，不要夸赞，不要直接重写代码。
```

## 8. 项目规则文件模板

放在仓库根目录（例如 `CLAUDE.md` 或同类的规则文件），每次会话自动带入。

```
# 项目规则

## 技术栈与结构
- 语言/框架/版本：...
- 目录结构：...
- 命名与风格：遵循 lint 配置

## 工作流
- 先读 docs/ 下相关需求与设计文档，再动手。
- 需求或设计有歧义时先提问，不要猜。
- 发现文档有问题时停下来报告，不要在代码里绕过。
- 每次只做一个小任务，只改任务范围内的文件。

## 禁止事项
- 不引入新依赖（需先征得同意）
- 不吞异常，不用默认值掩盖错误
- 不修改测试预期来让测试通过
- 不做未被要求的重构或功能
- 不提交密钥与敏感信息

## 完成标准
- lint、类型检查、相关测试通过
- 汇报：改动文件、与设计的偏离、不确定之处
```

## 9. 合并前检查清单

- [ ] 需求文档已确认，假设清单与未决问题已处理
- [ ] 设计与影响分析已确认，回滚方案可行
- [ ] 测试覆盖了每条验收标准与状态机的所有转换
- [ ] 自动检查全部通过
- [ ] 独立会话审查已完成，偏离点已处理
- [ ] 我已亲自审核 S/A/B 级内容
- [ ] 没有范围外改动，没有未批准依赖
- [ ] 文档已与最终实现同步
- [ ] 每一段核心代码我都能解释

## 10. 常见反模式

| 反模式 | 后果 | 对策 |
| --- | --- | --- |
| 一句话需求直接让AI写代码 | AI静默猜测，方向偏差 | 走完阶段1再开工 |
| 一次生成大量代码 | 审不动，只能盲信 | 拆小任务、小提交 |
| 看着代码写测试 | 测试只证明代码做了它做的事 | 测试先于实现，来源于需求 |
| 写代码的会话自己审查 | 上下文惯性，难发现问题 | 新会话审查 |
| 文档写完就不管 | 文档失效，失去事实来源作用 | 代码与文档冲突时先改文档 |
| 因为文档流畅就放松审核 | 流畅不等于正确 | 文档同样走门禁审核 |
| 遇到问题在代码里绕过 | 隐藏需求或设计缺陷 | 回退修改上游 |
| 全程让AI代劳，自己不理解 | 看懂了但写不出来，出问题无法排查 | 核心部分自己先写骨架或手推一遍 |

## 11. 度量与持续改进

每个迭代或每月回顾一次：

- 审查中发现的缺陷，是在哪个阶段引入的？（需求、设计、实现）
- 哪类错误AI反复出现？把它写进规则文件或检查清单。
- 哪个阶段的门禁形同虚设？收紧或简化。
- 提示词模板是否需要调整？

**对小任务可以裁剪流程：** 例如修一个小缺陷、改文案，可以只保留“失败用例 → 修复 → 自动检查 → 审查diff”。但凡涉及状态机、数据库结构、权限、资金或数据一致性，必须走完整流程。
